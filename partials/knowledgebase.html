1. Architecture at a glance

A single-page dashboard published as a claude.ai Artifact. The source is plain ES modules; a small build step turns them into a few static files that the Artifact serves. There is no server of our own: the page talks to the shared database, to Claude and to TradingView through the Artifact's built-in connectors.

  • Source: src/ (JavaScript modules, one responsibility per file), styles/ (CSS in cascade order, imported from styles/main.css), partials/ (Help, Data Refresh and Knowledge Base text) and index.html (the page shell).
  • Build: node tools/build.js bundles the source with esbuild into app.js (the small start-up file), hashed chunks/ (code-split, so Data Refresh, Strategies, Explorer and Trade Log download only when first opened) and styles.css. These outputs are never edited by hand.
  • Start-up: js/loader.js imports app.js, which loads the stock data from the database (a copy is kept in the browser, so repeat visits only download after a refresh), fetches the partials, then loads the application chunk. Every build gets an id so old and new files never mix.
  • Data: the stock list lives in the shared database (stockMeta and stockData), with researched factors and technical updates layered on top on load (§7). Nothing needs republishing when data is refreshed.
  • Hosting: every release is a new version of the same Artifact URL; only changed files are uploaded.

Rules the code follows

  • Imports are explicit; a module cannot assign to another module's variable; start-up code lives in init_*() functions called from src/main.js; unused code fails the lint.
  • Screens share behaviour through the modules above rather than copies, so a change to refresh batches, full screen or the phone layout is made once.
  • Tests: engine unit tests (CSV engines and refresh batches), a jsdom regression harness compared with stored snapshots, and four Chromium suites (smoke and layout including phone sizes, state, live ticker, imports).

2. How this screener stays up to date

The page is static and can't call outside services, so the Claude conversation that maintains it acts as the backend.

  • Fundamental Score: upload a screener.in CSV in the Fundamental job's panel on the Data Refresh page.
    • The file is saved in the artifact's asset store, with a record in fundamentalCsvUploadLog (§7), so a later conversation can score it without re-attaching.
    • Claude runs the 9-factor mechanical model every time.
    • Researched factors are kept separately in stockResearch and layered on top, so a refresh never overwrites them.
    • This is the only way a new stock enters the dashboard. A first-time ticker gets full onboarding.
  • Technical Score: upload a TradingView Growth List CSV in the Technical job's panel.
    • It is the sole source, and is pure arithmetic on RSI/MACD/price data.
    • It never onboards a new stock; unmatched symbols are skipped.
    • The old live TradingView fetch was retired on 2026-09-29.
  • Fundamental/Valuation research pass: retired 2026-09-29. These now update only from a fresh screener.in CSV.
  • Global & Macro Factors: its own manual "Refresh Data" button, limited to Strong/Good stocks. See Knowledge Base §6.
  • Manual refresh queue: the ↻ button on a stock writes a timestamped request to the database; Claude clears it when asked.
  • TradingView Watchlist Sync: manual only, no schedule. Rebuilds four lists from scratch on every run:
    • Alba Securities: every Strong or Good stock.
    • Alba - Green: Margin of Safety ≥ 0%.
    • Alba - Orange: −25% ≤ MoS < 0%.
    • Alba - Red: MoS < −25%.
    • Strong/Good stocks with no valuation data are left out of the three MoS lists.
    • Lists are deleted and recreated each run, so a stock can never linger after leaving its band.

3. Fundamental Score — stack & sources

Combines financial health, profitability, growth, valuation and governance into one score.

  • Model: 9 factors, weights summing to 10. Full breakdown and worked example in Help §1.
  • Source: a screener.in export CSV, uploaded on the Data Refresh page (§2). It is the sole, always-on source; there's no scraper or data-provider API.
  • Computed from the CSV: Financial Health, Profitability, Growth, Valuation, Earnings Predictability, Capital Reinvestment and Margin of Safety.
  • Proxies: Moat uses industry-relative capital efficiency; Governance uses Piotroski F-Score percentile plus pledge and holding changes. Both are pending individual research.
  • Peer set (v3, 2026-10-06):
    • Same Industry Group and same industry (the label after the · in the ticker field).
    • Falls back per metric to the Industry Group, then to all stocks, when fewer than 10 peers have data.
    • Margin of Safety always ranks against all stocks.
  • Engine: kept in the asset store as engine_v3.js.
  • Upload panel: shows new and dropped tickers before you commit. If the file browser doesn't open on your phone, open the page in your phone's own browser instead of inside the Claude app.

4. Technical Score — stack & sources

  • Refresh: manual only. Upload a Growth List CSV in the Technical job's panel; there's no schedule or live fetch (removed 2026-09-29).
  • Source: a TradingView Growth List export with 1-week/1-month price change, RSI(14) and MACD(12,26,9) level and signal.
  • BSE-only tickers: the dashboard stores a numeric BSE code as a placeholder. The tradingview-watchlist-symbol-mapping skill maps it to the TradingView alpha symbol so the row can be matched.
  • Computation: a deterministic 0–10 composite, with no buy/sell bucket labels (removed 2026-09-29).
    • MACD points: monthly weight 2.5, weekly weight 1.5, each × a fraction: 1 bullish above zero, 0.5 bearish above zero, 1/3 bullish below zero, 0 bearish below zero.
    • RSI points (per timeframe): 2.0 for 55–70, 1.2 for 45–55, 0.8 for 70 and above, 0.4 for 30–45, 0 below 30.
    • Valuation points: (pillars.val ÷ 10) × 2.0. Never touch or delete pillars.val.
    • Composite: the sum, rounded to 2 decimals.
  • Partial data: a blank component (often monthly MACD/RSI for newer tickers) is left out, and the sum is rescaled to 0–10 over the weights present.
    • Example: weekly MACD + weekly RSI + Valuation = 5.5 weight, so composite = (points ÷ 5.5) × 10.
    • With every component present this equals the plain sum.
    • technical.reason names what was missing.
  • Left untouched: a stock's existing technical block stays as is when it has no row in the CSV, or when pillars.val is missing.
  • No onboarding: symbols not already on the dashboard are skipped. New stocks come only from the Fundamental CSV (§3).
  • Price refresh: each import also updates matched stocks' current price (see v1.9).
  • Price history chart (optional, per stock): Weekly and Monthly candlestick bars from TradingView, shown in the Technical Score panel.
    • Pulled only when you want it: Refresh Technical Info in the stock's Live Data Refresh section (or in bulk from the Analysis screen). It fetches only the new weekly and monthly bars when history is already stored.
    • Refreshes fetch only the delta: when bars are already stored, just the bars since the last stored one are pulled (plus 3 of overlap), merged into the stored history and cross-checked against it. If the overlap no longer matches (for example after a split), it falls back to a full re-download. The first run for a stock still fetches the full 5 years.
    • Ticked on its own (nothing else flagged), the request only refreshes the price bars and needs no republish.
    • Up to 5 years of history or everything since listing, validated and stored in the priceHistory collection (§7). It never changes a score.
  • Upload panel: shows new and dropped tickers and a refresh scope preview, and saves the file to the asset store (§7).

History: from 2026-09-22 to 2026-09-29 the score came mainly from a live daily TradingView fetch. That scheduled task was deleted to save resources, and CSV upload is again the only mechanism.

5. Valuation — stack & sources

  • Source: one "Intrinsic Value" column from the uploaded screener.in CSV, carried through as is, not recomputed. Analyst price targets were removed 2026-09-29.
  • Margin of Safety = (Intrinsic Value − Current Price) ÷ Intrinsic Value.
  • Drives: the MoS %, the MoS badge on rows, and the green/orange/red MoS Rating filter.
  • Not a DCF: it has no discount-rate assumptions, and it is weakest for cyclical, asset-heavy businesses (shipping, dry bulk, commodities) where one year's EPS isn't representative.
  • Graham Number is a different figure. It comes from a separate CSV column.
    • It is shown read-only on the Margin of Safety factor card as a cross-check, and feeds no filter or score.
    • The two disagree by over 30% on 1,078 of 1,718 stocks that carry both (checked 2026-09-30). On OCCL, the Graham Number (₹172) implies fair value while Screener's figure (₹354.91) implies ~50% undervaluation.
    • Treat them as two independent opinions.
  • Refresh: tied 1:1 to the Fundamental CSV upload (§3). There's no separate research pass.
  • Retired 2026-09-30: a second "Computed Intrinsic Value" (a cyclical-normalized Graham Number) was dropped once Screener's own method proved more sophisticated. See §9.
  • Removed 2026-09-30: the 12-Month Price Target and FII Ownership Trend cells, including their fields and render code.

6. Global & Macro Information — stack & sources

  • What it is: a curated, sourced list of macro, commodity, currency and trade-policy linkages that can move the stock. No scoring.
  • Sources: sector-level web research for most stocks, individual research for large or newsworthy names.
  • Scope (since 2026-09-30): Strong or Good stocks only, about 487 of them, the same set the Watchlist Sync targets.
    • Hold and Avoid stocks keep an empty record until they reach Strong or Good.
    • The reason is the shared web-search quota (§2).
  • Bulk refresh: its own manual trigger on the Data Refresh page, independent of the Fundamental CSV, and needed less often since these linkages move slowly.
    • Prioritizes in-scope stocks with no research, then the most out of date, or a subset you name.
    • Updates each stock's globalFactors lists and sources in the database; no republish.
    • Never touches Fundamental, Valuation or Technical Score.
  • Single stock: Refresh Fundamental Info in the stock's Live Data Refresh section, in scope or not. It runs inside the page (no Claude chat) and refreshes the macro linkages and a new Critical news & world events block: up to 4 events (wars, sanctions, oil or commodity shocks, tariffs, policy, currency) tagged Helps, Hurts or Mixed with a one-line plain reason and a source.
    • It is context only and never changes a score. It sits above the Technical Score panel.
    • Events come from the TradingView headlines the refresh reads plus Claude's own knowledge (to about mid-2026). There is no live web search, so events from Claude's knowledge are labelled "may be dated".

8. Build, test and release

  1. Edit only src/, styles/, partials/ and index.html. The built files are generated.
  2. npm run check does everything before a release: build, "built files are up to date", syntax check, strict lint (undefined names, start-up order, unused code), the engine unit tests, the jsdom regression harness against tests/golden.json, and the Chromium suites. After a reviewed, intended change, npm run update-golden accepts the new snapshots.
  3. Bump the version badge in index.html, add a Version History entry here, and rebuild.
  4. Publish with the Artifact tool: the page shell plus only the files that changed (the hashed chunk files change on every build, so the old names are removed). Stock data, research and logs live in the database and never need republishing.
